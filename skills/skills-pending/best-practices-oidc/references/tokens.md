# Tokens

Three token types. **Never confuse their roles.** The ID Token authenticates. The access token authorizes. The refresh token renews.

## ID Token — the OIDC artifact

A signed JWT (JWS; optionally JWE) describing the authentication event.

**REQUIRED claims** (Core §2):
- `iss` — Issuer Identifier; HTTPS URL, no query, no fragment.
- `sub` — Subject Identifier; ≤255 ASCII chars, case-sensitive. The pair `(iss, sub)` is the **only** canonical, stable user key.
- `aud` — Audience; string or array; **MUST contain `client_id`**. If multi-valued, `azp` SHOULD be present.
- `exp` — Expiration (NumericDate, epoch seconds).
- `iat` — Issued-at time.

**Conditional / optional**: `auth_time` (REQUIRED when `max_age` was requested), `nonce` (REQUIRED if sent in the auth request; value MUST equal what the client sent), `acr` (assurance level), `amr` (methods array — `pwd`, `mfa`, `otp`, `hwk`, `fpt`, `sms`, `face`, `iris`, `swk`), `azp` (MUST be `client_id` when present).

**Signing** (Core §2): ID Tokens MUST be signed with JWS. MUST NOT use `alg:"none"` (except a response type returning no ID Token from the authorization endpoint, with the client registered for it). Default alg is `RS256` unless the client registered another `id_token_signed_response_alg`. If encrypted: sign then encrypt (nested JWT).

`sub` stability: `public` subject type → same `sub` everywhere; `pairwise` → different `sub` per client (per `sector_identifier_uri`).

## Access Token

- **Opaque (reference)**: random string; the RS calls `introspection_endpoint` (RFC 7662). Easy revocation, higher per-request latency.
- **JWT access token (RFC 9068)**: `typ` header SHOULD be `at+jwt` (the guard that stops an ID Token being accepted as an access token). REQUIRED claims: `iss`, `exp`, `aud`, `sub`, `client_id`, `iat`, `jti`. Optional: `scope`, `auth_time`, `acr`, `amr`, `groups`, `roles`, `entitlements`. `aud` MUST identify the resource server; RFC 8707 `resource` indicators request audience-restricted tokens. MUST NOT use `alg:"none"`.

**Rule**: never use the access token to identify the user — identity belongs to the ID Token (or UserInfo).

## Refresh Token

Opaque to the client. Single-use under rotation; sender-constrained for public clients (DPoP/mTLS). Absolute lifetime + inactivity timeout. Never log. (Rotation/reuse detail in `flows.md`.)

## JWT internals — JWS, JWE, algorithms

- **JWS** (RFC 7515): `BASE64URL(header).BASE64URL(payload).BASE64URL(signature)`.
- **JWE** (RFC 7516): encrypted JWT. **JWA** (RFC 7518): algorithm identifiers.

**Allow-list to verify against**:
- ID Token signing: `RS256` (mandatory baseline), `PS256`, `ES256`, `EdDSA` (plus the `*384`/`*512` siblings for symmetry).
- `HS256/384/512` — only for confidential clients (HMAC key = UTF-8 octets of `client_secret`, Core §10.1). Never expose HS to public clients; never share an HS key across many clients.
- **`alg:"none"`**: reject unconditionally.

**Algorithm-confusion attack**: a verifier that trusts the token's `alg` lets an attacker submit `alg:"HS256"` and HMAC the token using the RSA *public* key bytes as the secret. Mitigation: **pin allowed algs at the call site**, bind key type to algorithm, never pass the token's `alg` into the verifier.

**`kid` handling**: select the JWK by header `kid`; on a miss, refetch JWKS **once** (single-flight). Never honor embedded `jwk`/`jku`/`x5u` JWS headers — the attacker would pick the key.

**`crit` header**: a JWS verifier MUST understand any header listed in `crit`; reject an unrecognized critical header.

**JWKS fetching/caching**: cache with a TTL (≈10 min) honoring `Cache-Control`/`ETag`; one bounded entry per issuer; de-duplicate concurrent fetches (single-flight); 5s timeout; restrict to the discovered `jwks_uri` host (SSRF guard).

## `at_hash` / `c_hash` / `s_hash`

base64url of the left-most half of the hash of the ASCII octets of the target value, using the alg the ID Token is signed with (`RS256` → SHA-256, take the left 128 bits).
- `at_hash` — over `access_token`; REQUIRED when an ID Token is delivered alongside an access token via the authorization endpoint.
- `c_hash` — over `code`; REQUIRED in Hybrid ID Tokens issued at the authorization endpoint.
- `s_hash` — over `state`; FAPI 1.0 only, removed by FAPI 2.0.

## `nonce`

High-entropy, opaque, generated by the client per request. Bind it to the user-agent session (HttpOnly cookie or server-side session — never `localStorage`). REQUIRED in flows returning an ID Token from the authorization endpoint; RECOMMENDED in plain Code flow as defense-in-depth.

## Checklist — correct ID Token validator (Core §3.1.3.7)

Run in order:

1. Parse the JWT; reject a malformed header or claims set.
2. Reject `alg:"none"`. Pin the allowed algs (e.g. `[RS256, PS256, ES256, EdDSA]`).
3. If encrypted (JWE), decrypt with the client's registered decryption keys.
4. Locate the signing key by `kid` in the cached JWKS; on a miss, refetch JWKS once (single-flight).
5. Verify the JWS signature.
6. `iss` MUST **exactly** equal the discovered Issuer Identifier — byte compare, no trailing-slash normalization.
7. `aud` MUST contain `client_id`. Reject untrusted extra audiences.
8. If `azp` is present, it MUST equal `client_id`.
9. `exp` > now − skew; `iat` ≤ now + skew; optionally reject `iat` older than `maxAge`.
10. If `nonce` was sent, it MUST be present and equal the value sent.
11. If `auth_time` was requested or `max_age` was set, `auth_time` MUST be present and acceptable (re-auth if too elapsed).
12. If `acr` was requested, verify it.
13. If `at_hash`/`c_hash` is present (Hybrid/Implicit), compute and compare.
14. Return typed claims; never expose the raw JWT to higher layers.

Clock skew: default ±30s, configurable 0–60s. FAPI 2.0 allows up to 10s in the future, caps at 60s.
